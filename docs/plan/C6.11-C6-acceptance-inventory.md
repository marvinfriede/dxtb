# C6.11 — C6 acceptance inventory and D4 compatibility hardening

Base: `9a9ff116b7ce02ac33cc96b5df2108e6f63d46d5`

Branch: `claude/tender-dijkstra-cda42s`

## D4 targeted compatibility review

`DispersionD4.get_energy()` accepts both `DispersionD4Setup` and
`DispersionD4CoreSetup`, and still rejects unrelated objects with the
established `TypeError` text, `Setup in DispersionD4 is not of type
'DispersionD4Setup'.` The compatibility test asserts that text. It is retained
because it is the pre-Node legacy error contract; changing it to enumerate the
new internal representation would make callers observe a needless message
change.

Before this review, `dispersion_d4_energy()` rebuilt a call-local external D4
model and cutoff before checking the position dtype/device. Legacy and core
setups did raise the same `RuntimeError` and preserve the established messages,
but the core path did unnecessary reconstruction before rejecting invalid
inputs. The checks now run against the setup's number device and `rcov` dtype
before any core-to-legacy view is built. Tests cover both representations,
dtype and meta-device mismatch, that the reconstruction helper is not called
for rejected core inputs, and evaluation after explicit Node dtype conversion.

The structural review found that parameter entries preserve insertion order,
sparse keys, Python scalar types, and tensor leaves. The typed tensor wrapper
retains integer/bool tensor dtypes while converting floating tensors. Core
conversion copies references and does not normalize a mixed-dtype parameter
tuple; only a later explicit `Node.to(dtype=...)` converts floating children.
Atomic number tensors and model number tables remain integer dynamic children;
cutoff tensors, `rcov`/`r4r2`, model tensor tables, parameter tensors, and
optional compatibility charges remain dynamic children. Model/setup
reference-charge modes are separate static descriptors. The only external
strategy values in context are the supported stateless counting function and
damping class; evaluation creates a fresh damping instance. Conversion rejects
unsupported custom model/damping/counting strategies rather than silently
discarding their behavior. Direct legacy APIs continue to carry those
extensions.

## C6 acceptance inventory

The scoped family slices C6.1 through C6.10 are recorded complete in the
roadmap: ES2/ES3, AES2, GeneralizedBorn, D4SC and its authority fixes,
deterministic component ordering, Repulsion, ShortRangeBond, IES, Halogen, and
classical D4. Their single-System setup Nodes coexist with explicit legacy
compatibility routes. This inventory is a source/roadmap review, not a rerun of
every historical matrix; inherited numerical issues remain classified as in
the roadmap.

The source tree also contains shared `Classical`, `Interaction`, and cache base
classes. These are abstractions rather than additional physical setup families.
The inventory covers the concrete classical and interaction families present
under `src/dxtb/_src/components` at this revision.

### Component containers and functional descriptors

`ComponentList` stores an ordered Python list and C6.5 preserves first
occurrence input order. It remains a compatibility/container abstraction;
this package did not replace it with a Node. `ClassicalList` and
`InteractionList` still own component iteration, labels, legacy extension
dispatch, and packed-batch cache construction. `ClassicalListCache` and
`InteractionListCache` remain dictionary-backed adapters with their cull and
restore behavior. For a single System, `Model.setup()` no longer invokes
`ClassicalList.get_cache()` for exact built-ins and does not persist a generic
cache containing their setups. `System.classical_cache` is an on-demand
ordered compatibility view over family Nodes and separately stored
extension-only cache data. Packed Systems retain the complete legacy cache.
The property returns a fresh dictionary view on access; setup objects and
extension cache values retain their captured identities. Assigning or replacing
an entry in one returned view affects only that dictionary; it does not write
through to System-owned setup values or extension storage. Direct
`ClassicalList.get_cache()` remains unchanged.
Per-call interaction data is built through the interaction cache path; the
functional SCF map consumes its supported frozen descriptor rather than the
mutable interaction component.

B6a-Cache.1 establishes the single-System ownership boundary: exact Repulsion,
ShortRangeBond, IES, Halogen, classical D4, and D3 setups are built once through
their family setup routes, and `System.singlepoint()` consumes those captured
values. A System-boundary uniqueness check rejects distinct active
contributions with duplicate labels while preserving direct `ClassicalList`
construction behavior. It also rejects multiple exact instances of a
singular-setup family because each has one authoritative System field; multiple
D3 terms remain supported through identity-associated setup entries.
`ClassicalList.get_cache()` remains the unchanged direct compatibility API;
packed Systems still use it. Broader B6a remains partial because legacy
component/cache lifecycle APIs and compatibility-owner retirement are outside
this slice.

`ClassicalList.reset_all()` continues to reset the exact D3 compatibility
component: its `numbers` tensor is replaced by an equal-valued clone and its
legacy cache is invalidated. The captured single-System D3 Node remains the
authoritative setup, with unchanged identity, energy, position gradient, and
active parameter gradient across `Calculator.reset()`. The packed legacy D3
list route also retains equal energy after reset while observing the replaced
component tensor identity. This behavior is covered and requires no production
reset change.

`FunctionalInteractionEntry` and `FunctionalInteractionSet` are frozen
dataclasses, not registered `Node` classes or ordinary PyTorch pytree nodes.
Their `data` and `static` fields are ordered tuples; supported setup metadata
such as D4SC's immutable compatibility view is held in `static`. The existing
`tensor_leaves()` and `replace_tensor_leaves()` utilities recurse through
tensors, dataclasses, and tuples, so the current implicit tensor-tree adapter
can find and replace those supported leaves. They are intentionally not a
general object serializer: arbitrary mappings, lists, closures, or hidden
tensor state in custom extension objects are not traversed. Exact supported
interaction types are explicitly prepared; custom interaction extensions
retain the legacy route. Current functional FULL/implicit controls exercise
the supported descriptors. Their custom implicit tensor-tree traversal is
distinct from ordinary `torch.utils._pytree` registration; see the C6-Final.0
audit below.

### D4 performance characterization

Performance characterization of call-local D4 model/cutoff/damping
reconstruction was not performed in C6.11. The path intentionally avoids
persistent mutable-object caching; any optimization proposal should use a
separate measurement of both reconstruction and complete evaluation time.

### Remaining full-C6 work as recorded at C6.11

Full C6 acceptance still requires work beyond these family slices:

- Broader B6a still includes retirement of legacy component/cache lifecycle
  APIs and decisions for remaining compatibility adapters. B6a-Cache.1 closes
  generic built-in cache construction/storage for the single-System core; the
  on-demand `System.classical_cache` view remains for compatibility, and
  packed/custom paths keep legacy caches.
- At the C6.11 review point, Final B3b still required masks, index mappings,
  transform-critical gathers, and `batch_mode`/`dd` layout work. B3b-Final.0
  through B3b-Final.3 have since closed that staged-layout boundary; the
  remaining C6-Final.0 descriptor registration gap is documented below.
- `ClassicalList`, `InteractionList`, and their cache adapters remain
  compatibility containers for packed batches and custom extensions. The
  C6.5 insertion-order guarantee is complete; whole-container retirement or
  redesign is separate from that ordering correction.
- `FunctionalInteractionEntry` and `FunctionalInteractionSet` remain the
  current ordered functional SCF descriptor representation. Any generic
  static/dynamic Node conversion needs its own design and validation; the
  family-specific C6 migrations did not make these descriptors Nodes.
- Electric-field and field-gradient values remain per-evaluation call inputs
  under B7. They do not need persistent setup Nodes; their compatibility
  component/cache route remains part of the broader legacy-owner boundary.

The original C6.4c worker-mode NO2 NaN, intermittent E0 small-gap gradcheck,
ten GFN1 density-parity failures, and incompletely classified C6.7 broad-suite
failures remain unresolved. None is evidence that the C6.10 D4 migration
changed physical behavior. Broader C6 remains partial; this note does not
start DFT-D3 migration or claim full C6 acceptance.

## C6-Final.0 — descriptor tree and compatibility audit

Audit base: `c391a2d7bc564c75ffa7c2f92c46e912a0b19706`.

The executable probe is
[`test_c6_descriptor_tree_audit.py`](../../test/test_calculator/test_c6_descriptor_tree_audit.py).
On a real GFN2 `ExactSystemCore`, standard PyTorch pytree flattening treats
the frozen core as one opaque leaf. Flattening a real
`ClassicalTermDescriptor` or `InteractionTermDescriptor` does the same. A
tuple of descriptors is traversed as a tuple, but each descriptor remains an
opaque leaf; nested setup Node tensors are absent from that standard tree.
Flattening the nested setup Node directly exposes its dynamic tensor
children. The supported implicit tensor-tree adapter separately recurses
through dataclasses and tuples and observes the same nested tensor objects.
This proves present implicit-adapter visibility, but it does not satisfy a
future `ExactSystemCore` standard-pytree boundary.

The probe round-trips descriptor and setup trees, checks setup-leaf identity,
and compares dataclass traversal paths. The GFN1/GFN2 examples show that
descriptor structures differ: GFN1 has three classical terms and ES2/ES3
interactions; GFN2 has two classical terms and ES2/AES2/ES3/D4SC interactions.
The test-local probe passes (5 tests in each of the five approved Python/Torch
CPU environments). It
records the current opaque boundary; it does not implement or claim future
Node registration.

For GFN2/H2 on CPU float64, the actual GFN2 classical descriptor leaves
include D4 integer `numbers`/`model_numbers`, seven floating parameter-entry
tensors, floating `model_wf`/`model_rc6`/`rcov`/`r4r2`, and floating cutoff
children; Repulsion contributes float64 `arep`/`zeff`/`kexp`/`cutoff` and a
Boolean mask. Interaction leaves include ES2 Boolean masks, int64
`shells_to_atom`, and float64 Hubbard/exponent tensors; AES2 int64 numbers,
Boolean pair mask and float64 parameter/kernel tensors; ES3 float64 Hubbard
derivatives; D4SC int64 numbers and float64 parameter/model/radius/weight
tensors. `kind`, `label`, `position`, charge dependence, geometry-input
tuples, and setup type are static descriptor metadata. The descriptor stores
the exact existing setup Node by identity; its construction creates no second
parameter-tensor owner. These values are seen by the custom recursive walker,
but they disappear as dynamic leaves when the descriptor itself is passed to
standard PyTorch pytree traversal.

`FunctionalInteractionSet` is a call-local SCF adapter value, not persistent
System setup. Its tensors remain discoverable by the explicit
`tensor_leaves()`/`replace_tensor_leaves()` routines used by the supported
implicit route. This audit found no requirement to register that call-local
container itself. C6-Final.1 should register persistent classical and
interaction descriptors (or an ordered descriptor Node) with setup Nodes as
dynamic children and kind/label/position/configuration as static metadata. It
must not duplicate setup tensors or put setup Nodes in static context.

### Component and list boundary

The family setup migrations and B3b-Final.3 ordered descriptors satisfy the
single-System functional need for captured built-in setup ownership and
dispatch. They do not migrate the public `Component`, `Classical`,
`Interaction`, `ComponentList`, `ClassicalList`, `InteractionList`,
`ClassicalListCache`, or `InteractionListCache` types. Those remain mutable
legacy compatibility owners for direct Calculator use, packed modes 1/2,
custom extensions, lifecycle calls, and cache cull/restore behavior. This is
an explicit boundary, not evidence that the original C6 goal to migrate all
components and list containers has been fully met. C6 remains open until its
approved core descriptor/list representation is registered and its adapter
contract is accepted.

Legacy containers need not be retired solely to register the exact core
representation. C6-Final.1 should keep them outside the core and pass ordered
immutable descriptors plus existing setup Nodes to core evaluation. Their
public API retirement remains coordinated with E4.6/E6b compatibility policy
and must not become an unproven C8b dependency.

For structurally stackable groups, C8b should partition by a static descriptor
signature (ordered family kind, label, position, optional setup presence, and
family configuration) plus compatible dynamic leaf shapes/dtypes/devices.
Systems with absent terms or a different D3 count belong to another bucket;
no dummy physical terms may be inserted. Multiple D3 entries remain ordered
dynamic children. This is structural stacking only, not physical SCF `vmap`,
which remains E6a/E6b scope.

The executable structural comparison uses GFN1/H2 versus GFN2/H2 to show
different descriptor counts and families, then GFN2/H2 versus GFN2/LiH (both
two atoms) to hold descriptor metadata fixed while `ES2CoreSetup` shell
Hubbard and shell-to-atom map shapes differ. Existing
`test_exact_core_checks_ordered_d3_setup_coherency` and the D3 core-node/model
tests construct two distinct ordered D3 descriptors and verify their setup
identity. This establishes that method/composition/term-count and shell-shape
compatibility all matter to a stack bucket; it does not execute a mapped SCF.

Exact built-in classical outputs are ordered `(label, energy)` entries and
valid setup enforces unique active labels. `Result.cenergies` converts those
entries to a dictionary. Post-setup extension-label mutation is not a
supported update route: the compatibility cache is keyed under the label
captured at setup. The diagnostic mutation currently fails at cache lookup
instead of returning a misleading energy/result mapping. No production change
is justified; supported label changes require rebuilding Model/System.

The interaction adapter preserves descriptor position and verifies selected
component identity for D4SC setup authority. It then emits cache data keyed by
the active component label for the functional adapter. Duplicate or mutated
labels are not a supported way to transfer setup authority; custom interaction
types remain on the established compatibility route. Explicit electric-field
and field-gradient tensors remain call-local inputs, not persistent
descriptors. `FunctionalInteractionSet` remains the current call-local
ordered representation.

## C6-Final.1 — persistent descriptor Node registration

C6-Final.1 replaces only `ClassicalTermDescriptor` and
`InteractionTermDescriptor` with registered `tad_mctc.tree.Node` values.
Their existing setup Nodes are a single dynamic child; `kind`, `label`,
`position`, geometry inputs, and classical charge dependence are static
context. `ExactSystemCore`, `System`, and `Model` remain unregistered, and the
call-local `FunctionalInteractionSet` keeps its explicit tensor-tree adapter.

The production construction path still passes the already captured setup
object directly to each descriptor. Standard `torch.utils._pytree` traversal
now exposes the same setup tensor objects, and descriptor flatten/unflatten
preserves metadata, setup type, tensor values, and graph-connected leaves.
The descriptor pytree spec has no tensor-valued static context. Stacking two
independently built GFN2/H2 descriptor collections succeeds with matching
tree spec, leaf shapes, and dtypes; GFN1/GFN2 descriptor structures differ,
while GFN2/H2 and GFN2/LiH have equal metadata structure but incompatible
shell-resolved leaf shapes. C8b must partition on descriptor structure,
static configuration, dynamic leaf shape/dtype, and device policy. No dummy
terms or padding are introduced here.

`Node.to(dtype=...)` converts floating setup leaves and preserves integer and
Boolean structure and descriptor metadata. Tests cover D3 and AES2 setup
leaves. A representative Repulsion descriptor calculation matches the legacy
component route for energy, position gradient, active `element.H.arep`
gradient, mixed position/parameter derivative, and position JVP. The setup
child and its leaf tensors retain identity at initial descriptor construction;
independently created Systems have distinct storage.

C6-Final.1 does not prove whole-System transforms or mixed-System execution.
It closes only the persistent descriptor tree boundary. `ExactSystemCore`
still needs registration/enclosing-tree treatment in C8b. Broader C6 remains
open for cross-family numerical/transform acceptance and final legacy,
packed, and environment compatibility review; C8b is still not ready.

## C6-Final.1a — non-allocating descriptor coherence checks

`System._active_exact_core()` previously built temporary
`ClassicalTermDescriptor` and `InteractionTermDescriptor` Nodes to compare
the mutable compatibility façade against persistent descriptors. The
coherence check now builds lightweight local metadata tuples and compares
them directly with the captured Nodes. It still validates exact built-in
kind, label, ordered position, setup identity, classical charge dependence,
geometry inputs, D3 owner ordering, setup-reference identity, and active
integral index identity. It performs no tensor-value comparison, setup
reconstruction, copy, or detach. Descriptor Node schemas and pytree behavior
are unchanged.

Constructor instrumentation was enabled after setup. On the C6-Final.1a
base, a GFN1/H2 classical-only evaluation constructed 3 temporary classical
and 2 interaction descriptors; FULL and implicit-root evaluations each
constructed 9 and 6, respectively; three successive FULL evaluations
constructed 27 and 18. The optimized implementation constructed zero
temporary descriptors in all four cases. Setup-time descriptor construction
remains unchanged, and persistent descriptor tuple and setup Node identities
remain stable. Regression coverage also runs repeated A/B/A evaluation for
GFN1 and GFN2 and checks the FULL and implicit routes. A separate GFN2/H2
base instrumentation run counted 2 classical and 4 interaction temporary
descriptors for a classical-only evaluation, and 6 and 12 for one FULL or
implicit-root evaluation.

A warm single-thread CPU microbenchmark on an AMD EPYC 7763, Python 3.12/Torch
2.14.1 measured the isolated `_active_exact_core()` check over 21 samples of
100 calls each at 66.248 μs median (60.434–68.856) on the base and 10.185 μs
(10.083–11.194) after the change. The complete GFN1/H2 `System.singlepoint()`
median over 9 evaluations after 3 warmups was 120.143 ms (119.436–130.199)
on the base and 118.579 ms (118.409–122.018) after the change. The end-to-end
difference is within run variability and is not claimed as an SCF speedup.
The descriptor audit and B3b layout contract passed 64 tests. Model and
singlepoint controls passed 74 tests; their 10 existing GFN1 production/FULL
parity failures are the established inherited set. The focused allocation
tests passed in the available Python 3.12/Torch 2.14.1 CPU environment;
other approved environment results were not available in this checkout.
CUDA was unavailable. No physics, reference values, tolerances, or XFAILs
changed. Broader C6 remains open and C8b is not ready.
