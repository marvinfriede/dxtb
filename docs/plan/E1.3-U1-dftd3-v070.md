## Baseline and dependency compatibility

The reproduced baseline environment was Python 3.14.8, PyTorch 2.14.1+cpu,
tad-mctc 0.9.1, tad-dftd3 0.6.0, tad-dftd4 0.8.0, tad-multicharge 0.7.0,
PySCF 2.14.0, and tad-libcint 0.3.0. CUDA was unavailable. `pip check` reports
the known separately-installed legacy dispersion dependency conflicts; dxtb's
0.9.1 tad-mctc requirement was not changed.

The original public GFN1/PyTorch jacfwd characterization reproduces the
following failure in tad-dftd3 0.6.0:

```text
NotImplementedError: You must implement the jvp function for custom
autograd.Function to use it with forward mode AD.
```

The traceback reaches `system.singlepoint` → `_evaluate_classical_descriptor`
→ `dispersion_d3_energy` → `tad_dftd3.model.atomic_c6` →
`AtomicC6.apply` → missing `jvp`.

The v0.7.0 tag replaces `AtomicC6` with composite tensor operations and
changes `atomic_c6(numbers, weights, reference, chunk_size=None)` to
`atomic_c6(numbers, weights, reference)`. The tag still declares
`tad-mctc==0.8.0`, conflicting with dxtb's exact 0.9.1 pin. Direct import with
0.9.1 also fails because `tad_mctc.autograd.is_batched` was removed. Further
runtime incompatibilities include the removed `coordination_number` function
and renamed `storch.divide`/`storch.sqrt` helpers. dxtb's existing import shim
can bridge old names when used through dxtb, but that does not make the
upstream package directly usable or resolver-compatible.

The prepared upstream patch changes its dependency to
`tad-mctc>=0.9.1,<0.10`, adapts the CNModel, safe math and batching APIs, and
adds direct v0.9 import/transform tests. `setup.py egg_info` confirms the
resulting `Requires-Dist` range. The patch was tested against tad-mctc 0.9.1
without importing dxtb or activating its shim.

## Upstream correctness finding and patch

The v0.7.0 source has a second defect at `disp.py`: its Python branch skips
the ATM three-body term when the value of `s9` is zero. For a trainable zero
coefficient this disconnects the valid nonzero derivative. The public GFN1
H2O reproduction returned no gradient before the patch. After the patch, the
H2O total-energy derivative at `s9=0` is approximately
`1.9765725e-10`; the upstream standalone test matches a central finite
difference. The patch skips cubic-cost ATM work only for zero, ordinary,
non-differentiable `s9`; it evaluates the same term when `s9` is nonzero,
requires reverse gradients, or is wrapped by a forward/vmap transform.

The patch adds six upstream tests covering zero-`s9` finite-difference
derivative, JVP/jacfwd/reverse agreement, vmap with mixed position/parameter
derivatives, third position derivatives with active ATM, padded atomic-number
zeros, and fullgraph compilation of atomic C6. Result: **6 passed** on Python
3.14.8 / Torch 2.14.1+cpu / tad-mctc 0.9.1.

## dxtb adapter and public integration

dxtb's D3 adapter retains compatibility with both signatures. It forwards
`chunk_size` to the v0.6 API. For the v0.7 API, an explicit non-`None`
`chunk_size` emits a `DeprecationWarning` explaining that the new grouped C6
algorithm does not apply it; the option is not silently discarded. The
normal v0.7 path calls the new signature without the removed keyword. A
focused regression verifies this behavior.

The tagged v0.7 implementation needs the tested upstream patch above before
it can be used with dxtb's 0.9.1 environment. With that patched source on
`PYTHONPATH`, production `Model.setup()` GFN1/PyTorch Systems passed public
`System.singlepoint` transforms for H2, H2O, and CH4. Tests cover:

- JVP and jacfwd matching reverse gradients.
- Public vmap with three H2 conformers while atom count is two, plus mapped
  reverse gradients and one-lane-per-output Jacobian checks.
- Public GFN1/H2O jacfwd and E6a.3 mapped component Results.
- Reverse-over-reverse and third reverse derivatives, including a
  differentiable `s9=0` H2O ATM term.
- Model-owned gradients for each active D3 parameter (`s6`, `s8`, `s9`,
  `a1`, `a2`) against serial summed gradients.
- A mixed position/`s9` derivative and finite nonzero `s9=0` gradient.
- Complete Result/status preservation through existing E6a.3 tests.

With the patched v0.7 source on `PYTHONPATH`, this selection passed **125

An independent fixed-input C6 comparison used identical six-atom mixed
numbers including one zero-number padding atom, reference tables, dtype,
weights, and chunk size 2 versus v0.7's unchunked API. Atomic C6 outputs had
maximum absolute difference 0 and the padded row/column were exactly zero.
The existing D3 energy/reference and derivative tests also pass under both
the v0.6 baseline and patched v0.7 source.

## Performance and memory observations

On Python 3.14.8 / Torch 2.14.1+cpu, single-threaded atomic-C6 timing
(three calls, same seeded float64 inputs and four active elements) was:

| Atoms | v0.6 chunk 64 | v0.7 grouped | Process peak RSS v0.6 → v0.7 |
| ---: | ---: | ---: | ---: |
| 20 | 0.005131 s | 0.000927 s | 359.4 → 351.0 MB |
| 300 | 0.022180 s | 0.001407 s | 388.0 → 352.0 MB |
| 1000 | 0.211427 s | 0.007900 s | 471.0 → 370.8 MB |

Peak RSS is process-level and includes the imported PyTorch environment; it
is not a device tensor allocator measurement. For 1000 atoms, the dominant
estimated C6 intermediate is about 25.1 MB for the old chunk-64 path versus
1.57 MB for v0.7's ordinary four-element grouped path. The v0.7 transform-safe
path groups against all 119 elements and is estimated at 46.6 MB per 1000
atoms before output/workspace tensors. The final `1000 × 1000` C6 output
itself is 8 MB in float64. CUDA peak memory was not measurable here.

## Environment matrix and limitations

The candidate integration selection passed in all five available CPU
environments: Python 3.10.22 / Torch 2.6.0, Python 3.11.15 / Torch 2.8.0,
Python 3.12.10 / Torch 2.11.0, Python 3.12.10 / Torch 2.13.0, and Python
3.14.8 / Torch 2.14.1. Each had tad-mctc 0.9.1 and the same registered D4,
multicharge, PySCF, and libcint packages. No CUDA environment or
no-libcint profile was available.

The upstream release still needs the local patch to become resolver and API
compatible. No dxtb dependency pin was changed and no upstream code was
vendored. The exact upstream patch is ready for upstream review; until it is
accepted and released, the standard dxtb environment still installs D3 0.6.0
and its original public GFN1 forward-mode blocker remains.

Overall E1.3 is open. E6a and E3 are not closed automatically; each must rerun
its own full acceptance matrix against the released dependency. E1.3-U1 is
complete as a bounded v0.7 candidate investigation. Its proposed tag-based
patch is superseded as an integration target by the current-main reconciliation
in E1.3-U2.
